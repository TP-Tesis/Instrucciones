Stack tecnológico y despliegue · Simulador de riego presurizado

Con qué se construye y dónde vive

Cada herramienta con la razón por la que está, el reparto entre Render y Railway, lo que cuesta al mes, y los cuatro riesgos del despliegue que hay que atacar antes del día del experimento.

La regla que ordena todo lo que sigue. El día del experimento no se repite. Entre 25 y 35 estudiantes van a entrar al mismo tiempo, una sola vez, en una fecha fijada con el docente. Toda decisión de infraestructura de este documento se toma pensando en ese día: si algo puede fallar ese día, no entra.

Sección 1

Cómo se reparten Render y Railway

Render sirve la aplicación web como sitio estático. Railway aloja la API y la base de datos. Y el cálculo pesado no está en ninguno de los dos: corre en el equipo del estudiante.

Ese reparto no es arbitrario. Sale directo de la decisión de arquitectura de poner el motor de cálculo en el navegador: como el servidor no calcula hidráulica, lo que queda para la nube es liviano — cuentas, escenarios, versiones, eventos y cuestionarios. Eso cabe cómodo en un plan pequeño.

Una regla sobre las versiones. Al empezar el Sprint 1 se fija la versión exacta de cada herramienta y no se mueve hasta que termine el experimento. Actualizar una librería a mitad del estudio puede cambiar un resultado sin que nadie lo note, y después no hay forma de saber si la diferencia entre grupos fue la intervención o la actualización.

Sección 3

Cómo queda organizado el repositorio

Un solo repositorio con cuatro carpetas. El motor es un paquete aparte que la web y las pruebas importan igual, sin copiar archivos entre carpetas. Esa es la forma concreta que toma la decisión de arquitectura de tener un solo cálculo.

La dependencia que nunca debe existir. packages/motor no puede importar nada de apps/web ni de apps/api. Conviene dejarlo comprobado automáticamente en la integración continua, porque es la clase de regla que se rompe sin querer un martes cualquiera, y cuando se rompe se pierde la propiedad que hace verificable al motor.

Sección 4

La configuración concreta de cada servicio

Render · Static Site

La aplicación web

Root directory: la raíz del repositorio.
Build command: pnpm install && pnpm --filter web build
Publish directory: apps/web/dist
Redirect/Rewrite: /* → /index.html (tipo Rewrite), porque la navegación ocurre dentro de la aplicación.
Variable: la dirección pública de la API.

Railway · Servicio

La API

Build: pnpm install && pnpm --filter api build
Start: pnpm --filter api start
Antes de arrancar: aplicar las migraciones pendientes.
Comprobación de salud: una ruta que responda si la base está viva.
Variables: cadena de conexión, clave de firma de sesión, y el origen permitido — la dirección del sitio en Render.

Railway · PostgreSQL

La base de datos

Se agrega como servicio dentro del mismo proyecto y entrega su cadena de conexión a la API por variable interna.
Sobre la bitácora: al usuario con el que se conecta la API se le quitan los permisos de modificar y borrar sobre esa tabla. Así la regla de solo agregar deja de depender de que nadie se equivoque al programar.

GitHub Actions

La puerta de entrada

En cada envío: instalar, revisar tipos, correr las pruebas del motor, correr la verificación contra el método normalizado y comprobar que el motor no importa nada de las aplicaciones.
Si algo falla, no se despliega. Render y Railway solo publican desde la rama principal, y a la principal solo se llega con todo en verde.

Dos cosas que se olvidan siempre y cuestan una tarde. La primera: sin la regla de reescritura en Render, recargar la página en cualquier ruta que no sea la raíz devuelve un error. La segunda: como el sitio y la API están en dominios distintos, hay que declarar explícitamente en la API qué origen tiene permiso de llamarla. Las dos aparecen apenas se despliega por primera vez, no antes.

Sección 5

Los cuatro riesgos del despliegue

Son propios de esta combinación de servicios y del hecho de que el experimento ocurre una sola vez. Ninguno se resuelve programando mejor.

Riesgo 1 · El servicio que se duerme. En los planes gratuitos de este tipo de plataformas, un servidor que no recibe visitas se apaga y el primer acceso después tarda decenas de segundos. Si eso pasa cuando treinta estudiantes entran al mismo tiempo, la sesión arranca mal y la primera impresión del instrumento queda arruinada.

Cómo se ataca: la API va en un plan de pago en Railway, que no se suspende. Y el sitio va en Render como estático, que tampoco se duerme porque no ejecuta nada. La combinación está elegida exactamente por esto.

Riesgo 2 · La base de datos gratuita que caduca. Las bases gratuitas de estas plataformas suelen tener fecha de vencimiento. Si vence entre el pretest y el postest, se pierde el punto de partida de cada estudiante y el estudio entero se cae.

Cómo se ataca: la base va en Railway dentro del plan de pago, y además se hace una copia manual antes y después de cada sesión con estudiantes, guardada fuera de la plataforma.

Riesgo 3 · El equipo del laboratorio no da para el 3D. La vista tridimensional exige aceleración gráfica. Si las computadoras de la UNDAC no la tienen, el grupo con 3D no puede cumplir sus dos tareas y la hipótesis secundaria se queda sin datos.

Cómo se ataca: hay que medirlo en el equipamiento real antes del Sprint 4, no el día de la sesión. Ya está como criterio de aceptación de la historia HU-23, pero la medición hay que pedirla al docente con anticipación.

Riesgo 4 · La conexión del aula. El caso de estudio describe conectividad variable. Si la aplicación dependiera de la red para calcular, la intervención dejaría de ser inmediata justo donde se la mide.

Cómo se ataca: ya está resuelto por arquitectura — el cálculo corre en el equipo del estudiante y los eventos se acumulan en una cola que reintenta. Lo que falta es probarlo con la red degradada a propósito antes de la sesión real.

Sección 7

Cuándo se despliega cada cosa

Pediste que al terminar la aplicación esté completamente desplegada. La forma de conseguirlo no es desplegar al final: es desplegar en la primera semana, cuando todavía no hay nada que desplegar.

Se llama esqueleto caminante: una versión mínima que atraviesa todas las capas — una página que llama a la API, que consulta la base, y responde — publicada de verdad en Render y Railway. No hace nada útil, y esa es la gracia: sirve para descubrir en la semana 1 los problemas de permisos, de origen permitido, de variables y de migraciones, en vez de descubrirlos en la semana 16 con el experimento encima.

Lo que esto implica para el backlog. El esqueleto caminante no es ninguna de las 30 historias actuales, y sin embargo es lo primero que hay que hacer. Hay dos salidas: agregarlo como historia del Sprint 1 — pasaríamos a 31 — o tratarlo como tarea técnica dentro de la historia del motor. Recomiendo lo primero, porque una tarea que no está en el backlog es una tarea que se posterga.

Sección 8

Lo que queda por decidir

  • Quién paga y con qué tarjeta. Railway necesita un medio de pago desde el primer día. Son cinco dólares al mes, pero si la tarjeta falla a mitad del estudio el servicio se suspende y el dato del día se pierde. Conviene resolverlo esta semana, no en el Sprint 4.
  • Qué pasa después de sustentar. Si el servicio se apaga, el jurado no puede volver a entrar. Vale la pena dejarlo encendido al menos hasta que el trabajo esté aprobado, y prever el costo de esos meses.
  • Dónde se hace el análisis: R o Python. No afecta al despliegue, pero sí a qué columnas tiene que traer la exportación. Conviene fijarlo antes del Sprint 4.
  • Si se usa un dominio propio. Puramente estético. Doce dólares al año, y hace que la dirección que se muestre en la sustentación se vea como un producto y no como una prueba.
  • Versiones exactas de cada herramienta. Se fijan al abrir el Sprint 1 y no se mueven hasta terminar el experimento.
